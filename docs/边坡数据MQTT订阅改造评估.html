边坡数据：定时拉取 → MQTT 订阅 · 改造评估

2026-11-01 · 仅评估，未改业务代码 · 基于现网 BDLX 小时拉取 + 已有 MQTT 接入骨架
结论先看：若厂商已按现有入模字段往 MQTT 推 GNSS（尤其 sn/baseX/baseY/baseZ/dateTime）， 对本系统而言改动属 小～中——订阅与落库链路已经存在。 若还要求「完全替代 BDLX」的雨量、告警、长历史回补、派生量与现网逐字段一致，则升到 中～大，且很大一块取决于对方是否提供 MQTT 主题与报文，不在我们代码里。

2. 目标（To-Be）几种口径

口径含义改动量
A. 仅位移改 MQTT GNSS 最新值以订阅为准；BDLX 可关或降级为兜底 小～中
B. 位移 MQTT + 派生量本地算 平面/速率/加速度/方位由时序计算 中
C. 完全去掉 BDLX 雨量、告警也改推送或其它源 + 本地阈值 大（多源协同）
前置条件（决定能不能做、做多大）：对方是否提供 Broker 地址、账号、Topic、QoS、报文 JSON 样例、推送频率、断线重连与补传策略。 若对方没有 MQTT，只有 HTTP（如 8088），则「改成 MQTT」本身不成立，应评估「改成 8088 定时/按需拉」——那是另一条方案。

范围条件估时风险

5. 风险与依赖

  • 外部依赖最大：没有 MQTT 推送就谈不上「改成订阅」；8088 目前是 HTTP 文档，不等于已有 MQTT。
  • 静默风险：订阅模式下设备不推或网络断，大屏会停在旧值；需心跳/超时离线与补拉策略。
  • 历史空洞：MQTT 通常只给「当前点」；长历史仍要 HTTP 区间查询或库内已存时序。
  • 验证码：仅位移走 MQTT 且关掉 BDLX 位移拉，可减少验证码；若雨量/告警仍走 BDLX，验证码问题仍在。
  • Clean Session / 持久会话：现客户端 cleanSession=true，断线期间消息可能丢，需与厂商约定 QoS 与补传。

6. 推荐实施步骤（方案）

  1. 澄清来源：向厂商确认边坡 GNSS 是否已有 MQTT；拿到 Broker、Topic、样例 JSON、频率。若无，改评估「8088 HTTP 拉」而非 MQTT。
  2. 对照报文：与 SensorPayloadIngestor 字段表对齐（sn、baseX/Y/Z 或 x/y/h、时间、单位）。
  3. 双跑试点：配置订阅，BDLX 仍开；对比同 SN 最新值与时序差异。
  4. 定主备：MQTT 为主后，BDLX 降为「超时未更新则拉一次」或关闭位移部分。
  5. 按需增强：本地算平面/速率；告警改阈值；雨量另源——再决定能否关 BDLX。
  6. 验收：断网恢复、夜间静默、重启 warmup、大屏弹窗字段完整性。
